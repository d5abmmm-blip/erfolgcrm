# Сервер потерян — как вернуть компанию к работе

Этот документ — на самый плохой день: боевого сервера больше нет (сгорел, удалён
хостером, потерян доступ). Он же годится для планового переезда на другой сервер.

`docs/backup-runbook.md` отвечает на вопрос «как проверить копию **на живом
сервере**». Здесь — «живого сервера нет, что делать».

> **Сколько времени займёт:** около 1–2 часов при наличии всего из раздела 1.
> Данные вернутся на момент последнего ночного бэкапа (03:00).

---

## 1. Что нужно иметь ДО катастрофы

Без этого восстановление невозможно или неполно. Проверьте, что всё это лежит
вне сервера — у директора и в менеджере паролей.

| #   | Что                                                           | Без него получится                                               |
| --- | ------------------------------------------------------------- | ---------------------------------------------------------------- |
| 1   | **Дамп базы** `erfolg_prod_auto_*.dump`                       | ничего                                                           |
| 2   | **Архив файлов** `erfolg_prod_files_*.tar.gz`                 | база вернётся, но сканы и фото будут битыми ссылками             |
| 3   | **`.env` боевого сервера** (или хотя бы `PII_ENCRYPTION_KEY`) | **ФИО и телефоны физлиц останутся нечитаемым мусором навсегда**  |
| 4   | **`docker-compose.server.yml`**                               | приложение поднимется с неверным адресом API и без тома вложений |
| 5   | **Доступ к репозиторию** кода                                 | нечего собирать                                                  |
| 6   | **Права на домен** `erfolgmt.ru`                              | сайт не будет открываться по своему адресу                       |

Пункты 3 и 4 ночной бэкап складывает в отдельный архив
`/root/backups/erfolg_prod_secrets_*.tar.gz` (права 600).

> ⚠️ **Но этот архив лежит на том же сервере.** Если сервер потерян, потерян и он.
> Копия обязана храниться **вне сервера** — в менеджере паролей директора или
> распечатанной в сейфе. Порядок — `docs/backup-runbook.md`, раздел «Копия ключа
> вне сервера». Если вы читаете это заранее, а копии наружу нет — сделайте сейчас,
> это 5 минут и единственное, что нельзя восполнить потом.

Проверить, что ключ вообще рабочий, можно не дожидаясь катастрофы: еженедельная
проверка `verify-restore.sh` разворачивает свежую копию и **расшифровывает одно ФИО**.
Строка `ПДн расшифровываются` в `/root/backups/verify.log` — доказательство, что ключ
подходит к копии.

Содержимое `docker-compose.server.yml` (на случай, если копии не осталось):
он задаёт `VITE_API_URL=https://crm.erfolgmt.ru`, пустой
`VITE_TENANT_DOMAIN_SUFFIX` и монтирует том `storage_data` в `/data/storage`
у контейнера api.

## 2. Порядок восстановления

### Шаг 1. Новый сервер

Ubuntu 22.04/24.04, 2+ ГБ памяти, 40+ ГБ диска, root-доступ. **Хостинг в РФ** —
в базе персональные данные граждан РФ (152-ФЗ).

```bash
apt update && apt install -y docker.io docker-compose-plugin git curl
```

### Шаг 2. Код

```bash
mkdir -p /root/erfolgcrm && cd /root/erfolgcrm
git clone <адрес репозитория> .
```

### Шаг 3. Секреты

Если сохранён архив конфигурации — распаковать его в корень проекта:

```bash
tar xzf /root/erfolg_prod_secrets_<дата>.tar.gz -C /root/erfolgcrm
```

Если архива нет, положить сохранённые `.env` и `docker-compose.server.yml` руками
в `/root/erfolgcrm/`.

```bash
chmod 600 /root/erfolgcrm/.env
grep -c PII_ENCRYPTION_KEY /root/erfolgcrm/.env   # должно быть 1
```

> Если `.env` не сохранился, но есть дамп: система поднимется, но **ФИО и
> телефоны физлиц не расшифруются**. Организации, заявки, суммы, счета и история
> при этом целы — они не шифруются. Восстанавливать такие ПДн придётся из
> первичных документов вручную.

### Шаг 4. Поднять базу и Redis

```bash
cd /root/erfolgcrm
docker compose -f docker-compose.prod.yml -f docker-compose.server.yml up -d postgres redis
docker compose -f docker-compose.prod.yml ps      # оба running
```

### Шаг 5. Залить базу из копии

```bash
# скопировать дамп на сервер, затем:
docker exec -i erfolgcrm-postgres-prod pg_restore -U erfolg -d erfolg_prod \
  --clean --if-exists --no-owner --no-privileges < /root/erfolg_prod_auto_<дата>.dump
```

Если база `erfolg_prod` ещё не создана — создать до восстановления:

```bash
docker exec erfolgcrm-postgres-prod createdb -U erfolg erfolg_prod
```

### Шаг 6. Вернуть файлы вложений

```bash
docker compose -f docker-compose.prod.yml -f docker-compose.server.yml up -d api
VOL=$(docker inspect erfolgcrm-api-prod \
  -f '{{range .Mounts}}{{if eq .Destination "/data/storage"}}{{.Name}}{{end}}{{end}}')
VP=$(docker volume inspect "$VOL" -f '{{ .Mountpoint }}')
tar xzf /root/erfolg_prod_files_<дата>.tar.gz -C "$VP"
```

### Шаг 7. Миграции и права доступа базы

```bash
docker compose -f docker-compose.prod.yml -f docker-compose.server.yml \
  run --rm --no-deps -T api sh -c 'cd /app && pnpm --filter @erfolg/db migrate'
```

Роль приложения `app_runtime` и построчная защита (RLS) приезжают вместе с дампом.
Пересоздавать их скриптом `setup-rls` нужно, только если после восстановления
приложение жалуется на доступ к таблицам — тогда передать скрипту **текущий**
пароль `app_runtime` из `DATABASE_URL`, иначе приложение потеряет доступ к базе.

### Шаг 8. Поднять всё

```bash
docker compose -f docker-compose.prod.yml -f docker-compose.server.yml up -d
docker compose -f docker-compose.prod.yml ps
curl -s 127.0.0.1:3030/health          # {"status":"ok"}
```

Контейнер api может показывать `unhealthy` — это косметика встроенной проверки,
приложение при этом работает (проверяется тем же `curl` выше).

### Шаг 9. Домен и TLS

Направить `crm.erfolgmt.ru` на IP нового сервера у регистратора, поднять Caddy
(или другой прокси) с автоматическим сертификатом на этот домен, проксируя
на `127.0.0.1:8080` (веб) и `127.0.0.1:3030` (API).

DNS обновляется до нескольких часов — до этого сайт может открываться не у всех.

### Шаг 10. Вернуть бэкапы

Сразу, не откладывая:

```bash
chmod +x /root/erfolgcrm/scripts/prod/*.sh
crontab -e
# 0 3 * * * /bin/bash /root/erfolgcrm/scripts/prod/backup-db.sh >> /root/backups/backup.log 2>&1
# 30 4 * * 0 /bin/bash /root/erfolgcrm/scripts/prod/verify-restore.sh >> /root/backups/verify.log 2>&1
/bin/bash /root/erfolgcrm/scripts/prod/backup-db.sh && ls -laht /root/backups | head
```

## 3. Проверка, что восстановились по-настоящему

Мало увидеть, что сайт открылся. Проверьте по порядку:

| #   | Что проверить            | Как                                                                               |
| --- | ------------------------ | --------------------------------------------------------------------------------- |
| 1   | Вход работает            | зайти директором                                                                  |
| 2   | Данные на месте          | список клиентов и заявок не пустой, числа похожи на ожидаемые                     |
| 3   | **ПДн расшифровываются** | открыть карточку клиента-**физлица**: ФИО и телефон читаются, а не мусор          |
| 4   | Вложения открываются     | открыть заявку со сканом или фото и скачать файл                                  |
| 5   | Печать документов        | распечатать любой акт в PDF                                                       |
| 6   | Почта                    | Настройки → Почта: подключение к ящику проходит                                   |
| 7   | Фоновые задачи           | в логах api нет повторяющихся ошибок: `docker logs erfolgcrm-api-prod --tail 100` |

**Пункт 3 — главный.** Именно он отличает «база залилась» от «компания вернулась
к работе». Если ФИО физлиц не читаются — значит `PII_ENCRYPTION_KEY` не тот,
и надо искать правильный, пока не поздно.

## 4. Частые грабли

| Симптом                                 | Причина                                                      | Что делать                                                       |
| --------------------------------------- | ------------------------------------------------------------ | ---------------------------------------------------------------- |
| ФИО физлиц — набор символов             | `PII_ENCRYPTION_KEY` не совпадает с тем, которым шифровали   | взять ключ из сохранённого `.env` того сервера; другого пути нет |
| Вложения не открываются                 | не распакован архив файлов, либо распакован не в тот том     | шаг 6                                                            |
| Сайт открывается, но данные не грузятся | не применён `docker-compose.server.yml` → неверный адрес API | шаг 3 и 8                                                        |
| Приложение не видит таблиц              | роль `app_runtime` без прав                                  | см. шаг 7                                                        |
| Сайт не открывается по домену           | DNS ещё не обновился или прокси не настроен                  | шаг 9                                                            |

---

## 5. Если восстанавливать некому

Система собрана на обычных, широко распространённых вещах: Docker, PostgreSQL,
Node.js. Любой системный администратор, знакомый с Docker, поднимет её по этому
документу. Специальных знаний именно об ErfolgCRM для восстановления не требуется —
кроме одного: **без `PII_ENCRYPTION_KEY` персональные данные физлиц не вернуть**,
и это не чинится ни деньгами, ни временем.
