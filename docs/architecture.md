# Архитектура ErfolgCRM

Обновлено 2026-07-20. Документ описывает систему **такой, какая она есть на
боевом сервере**, а не планы. Прежняя версия описывала отменённую модель «CRM как
сервис для многих компаний» — с порталом покупателей, биллингом и Terraform,
которых не существует.

## Что это за система

CRM сервисного центра медицинской техники. Работает **для одной компании** —
ООО «Эрфольг». Многокомпанейный код в системе остался (у каждой строки в базе
есть признак компании, отдельный демо-стенд живёт рядом), но продуктом для
многих компаний она не является и не продаётся.

## Как развёрнута

```
                     Интернет
                        │
                 crm.erfolgmt.ru
                        │
              ┌─────────▼─────────┐
              │  Caddy на хосте   │  TLS, сертификат обновляется сам
              └────┬─────────┬────┘
                   │         │
        127.0.0.1:8080   127.0.0.1:3030
                   │         │
   ┌───────────────▼──┐  ┌───▼──────────────────────────┐
   │ web  (nginx)     │  │ api (Node)                   │
   │ статика React    │  │ • tRPC                       │
   └──────────────────┘  │ • права по ролям             │
                         │ • журнал действий            │
                         │ • фоновые задачи (в этом же  │
                         │   процессе, 10 очередей)     │
                         └──┬──────────┬────────────────┘
                            │          │
                     ┌──────▼───┐  ┌───▼────┐   ┌──────────────────┐
                     │PostgreSQL│  │ Redis  │   │ том storage_data │
                     │   16     │  │        │   │  файлы, сканы    │
                     └──────────┘  └────────┘   └──────────────────┘
```

Один сервер, четыре контейнера Docker Compose (`api`, `web`, `postgres`, `redis`).
Файлы вложений лежат **локально в томе**, не в облачном хранилище.

Конфигурация: `docker-compose.prod.yml` из репозитория + `docker-compose.server.yml`,
который есть **только на сервере** (задаёт публичный адрес API и том вложений).

Порядок восстановления и переезда — `docs/disaster-recovery.md`.
Бэкапы — `docs/backup-runbook.md`.

## Защита данных между компаниями — что работает на самом деле

В системе есть демо-стенд рядом с боевыми данными, поэтому разделение важно.
Работают три вещи:

1. **`withTenantTx`** — все запросы к базе идут через неё; она открывает
   транзакцию, объявляя базе, с какой компанией работаем. Используется
   практически во всех модулях.
2. **RLS в PostgreSQL** — на таблицах с признаком компании стоят политики: даже
   если в запросе забыть условие, база не отдаст чужие строки.
3. **Тесты**, проверяющие, что запрос из-под одной компании не достаёт данные другой.

> Ранее этот документ обещал пять слоёв защиты. Двух из них не существует:
> функция-обёртка `tenantScoped()` не вызывается нигде, а ESLint-правила,
> которое якобы запрещает запросы без неё, в проекте нет. Обещание убрано,
> чтобы никто не считал защищённым то, что не защищено.

## Как устроен код

```
apps/
  api/   — сервер: tRPC-роутеры, бизнес-логика, фоновые задачи
  web/   — интерфейс: React + мобильная версия для инженеров (PWA)
packages/
  db/     — схема базы, миграции, шифрование персональных данных
  shared/ — общие типы и правила для сервера и интерфейса
```

Модуль на сервере:

```
apps/api/src/modules/<название>/
├── repository.ts  — запросы к базе
├── service.ts     — бизнес-логика
├── router.ts      — точки входа (tRPC)
└── __tests__/
```

## Стек

| Слой | Что |
|---|---|
| Интерфейс | React 19, Vite 6, Tailwind 4, TanStack Query 5, wouter |
| Сервер | Node.js 22, Express 5, tRPC 11, Drizzle 0.45, Argon2id, BullMQ |
| База | PostgreSQL 16 + pgcrypto + RLS |
| Файлы | локальный том на сервере |
| Кэш и очереди | Redis 7 |
| Telegram | внутри процесса api (отдельного бота-процесса нет) |
| Развёртывание | Docker Compose + Caddy на одном сервере |

## Персональные данные

ФИО, телефоны и адреса физлиц, а также тексты писем **шифруются в базе**
(pgcrypto). Ключ — `PII_ENCRYPTION_KEY` в `.env` сервера, существует в одном
экземпляре. Подробности и обязанности компании — `docs/152-fz-compliance.md`.

## Мелочи, о которых стоит знать

- Идентификаторы — UUID (версия 7, с меткой времени: лучше ложатся в индексы).
- Признак компании обязателен на всех таблицах, кроме служебных.
- Фоновые задачи живут **в том же процессе**, что и API, и делят с ним
  подключения к базе. Отдельного воркер-процесса нет.
- Контейнер `api` может показывать `unhealthy` — это особенность встроенной
  проверки, приложение при этом работает.
- Папка `infra/terraform/` пустая: инфраструктура настраивается руками,
  автоматизации развёртывания нет.
